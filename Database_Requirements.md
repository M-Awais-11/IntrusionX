# Database Requirements
## AI-Powered Intelligent Intrusion Detection System with Agentic AI

### 1. Overview

This document defines the database requirements for the AI-Powered Intelligent Intrusion Detection System based on the CIC-IDS2017 cybersecurity dataset.

The database will manage network traffic records, intrusion detection results, attack classifications, machine learning models, security alerts, and Agentic AI activities.

**Recommended Database:** PostgreSQL

### 2. Database Objectives

The database should support the following functionalities:

- Store and manage processed network traffic records.
- Maintain information about datasets and their sources.
- Store machine learning prediction results.
- Maintain attack categories and their classifications.
- Record detected security threats and generate alerts.
- Track trained ML models and their versions.
- Store AI agent tasks, decisions, and execution logs.
- Maintain historical detection records for analysis.
- Support dashboard visualization and reporting.

### 3. Required Database Tables

The database should initially include the following 10 core tables.

#### 3.1 `datasets`

Stores information about datasets used in the system.

| Column | Data Type | Description |
|---|---|---|
| id | BIGSERIAL | Primary Key |
| name | VARCHAR(255) | Dataset name |
| source | VARCHAR(500) | Dataset source |
| version | VARCHAR(100) | Dataset version |
| description | TEXT | Dataset description |
| total_records | BIGINT | Total number of records |
| created_at | TIMESTAMP | Creation date |

#### 3.2 `network_flows`

Stores network traffic flow records and their extracted features.

| Column | Data Type | Description |
|---|---|---|
| id | BIGSERIAL | Primary Key |
| dataset_id | BIGINT | Foreign Key |
| flow_id | VARCHAR(255) | Unique flow identifier |
| source_ip | VARCHAR(45) | Source IP address |
| destination_ip | VARCHAR(45) | Destination IP address |
| source_port | INTEGER | Source port |
| destination_port | INTEGER | Destination port |
| protocol | INTEGER | Network protocol |
| flow_duration | BIGINT | Flow duration |
| flow_features | JSONB | Extracted network traffic features |
| actual_label | VARCHAR(100) | Actual dataset label |
| created_at | TIMESTAMP | Record creation date |

Note: Additional CIC-IDS2017 features should be stored appropriately in `flow_features` or optimized relational columns.

#### 3.3 `attack_types`

Maintains the different types of network attacks.

| Column | Data Type | Description |
|---|---|---|
| id | BIGSERIAL | Primary Key |
| attack_name | VARCHAR(100) | Attack name |
| category | VARCHAR(100) | Attack category |
| description | TEXT | Attack description |
| severity | VARCHAR(50) | Severity level |

Examples:
- BENIGN
- DDoS
- DoS
- PortScan
- Bot
- Infiltration
- Brute Force
- Web Attack

#### 3.4 `model_versions`

Maintains information about trained machine learning models.

| Column | Data Type | Description |
|---|---|---|
| id | BIGSERIAL | Primary Key |
| model_name | VARCHAR(255) | Model name |
| algorithm | VARCHAR(100) | ML algorithm |
| version | VARCHAR(50) | Model version |
| model_path | VARCHAR(500) | Model file location |
| training_dataset_id | BIGINT | Foreign Key |
| training_date | TIMESTAMP | Training date |
| status | VARCHAR(50) | Model status |

#### 3.5 `detection_results`

Stores predictions generated by machine learning models.

| Column | Data Type | Description |
|---|---|---|
| id | BIGSERIAL | Primary Key |
| network_flow_id | BIGINT | Foreign Key |
| model_id | BIGINT | Foreign Key |
| attack_type_id | BIGINT | Foreign Key |
| predicted_label | VARCHAR(100) | Predicted class |
| confidence_score | FLOAT | Prediction confidence |
| is_malicious | BOOLEAN | Whether traffic is malicious |
| detected_at | TIMESTAMP | Detection timestamp |

#### 3.6 `security_alerts`

Stores security alerts generated from suspicious network activities.

| Column | Data Type | Description |
|---|---|---|
| id | BIGSERIAL | Primary Key |
| detection_result_id | BIGINT | Foreign Key |
| alert_title | VARCHAR(255) | Alert title |
| alert_description | TEXT | Alert details |
| severity | VARCHAR(50) | Alert severity |
| status | VARCHAR(50) | Alert status |
| created_at | TIMESTAMP | Alert creation date |

#### 3.7 `ai_agents`

Maintains information about the AI agents available in the system.

| Column | Data Type | Description |
|---|---|---|
| id | BIGSERIAL | Primary Key |
| agent_name | VARCHAR(255) | Agent name |
| agent_type | VARCHAR(100) | Agent type |
| description | TEXT | Agent responsibilities |
| status | VARCHAR(50) | Agent status |
| created_at | TIMESTAMP | Creation date |

#### 3.8 `agent_tasks`

Stores tasks assigned to or initiated by AI agents.

| Column | Data Type | Description |
|---|---|---|
| id | BIGSERIAL | Primary Key |
| agent_id | BIGINT | Foreign Key |
| detection_result_id | BIGINT | Foreign Key |
| task_type | VARCHAR(100) | Task category |
| task_description | TEXT | Task details |
| status | VARCHAR(50) | Task status |
| started_at | TIMESTAMP | Start time |
| completed_at | TIMESTAMP | Completion time |

#### 3.9 `agent_decisions`

Stores decisions and analysis generated by AI agents.

| Column | Data Type | Description |
|---|---|---|
| id | BIGSERIAL | Primary Key |
| task_id | BIGINT | Foreign Key |
| decision_type | VARCHAR(100) | Decision category |
| analysis | TEXT | Agent analysis |
| reasoning_summary | TEXT | Decision explanation |
| recommended_action | TEXT | Recommended response |
| created_at | TIMESTAMP | Decision timestamp |

#### 3.10 `agent_logs`

Maintains execution logs and activities performed by AI agents.

| Column | Data Type | Description |
|---|---|---|
| id | BIGSERIAL | Primary Key |
| agent_id | BIGINT | Foreign Key |
| task_id | BIGINT | Foreign Key |
| log_level | VARCHAR(50) | Log level |
| message | TEXT | Log message |
| execution_status | VARCHAR(50) | Execution status |
| created_at | TIMESTAMP | Log timestamp |

### 4. Database Relationships

The database should implement the following relationships using primary keys and foreign keys.

1. One dataset can contain multiple network flow records.
2. One dataset can be associated with multiple trained models.
3. One network flow can have one or more detection results.
4. One attack type can be associated with multiple detection results.
5. One ML model can generate multiple detection results.
6. One detection result can generate security alerts.
7. One AI agent can perform multiple tasks.
8. One detection result can be analyzed through agent tasks.
9. One agent task can produce multiple decisions.
10. One AI agent can generate multiple execution logs.

### 5. Technical Requirements

The database implementation should follow these requirements:

- Use PostgreSQL as the primary relational database.
- Implement proper primary keys and foreign key constraints.
- Use appropriate indexes for frequently queried columns.
- Use JSONB for flexible storage of extracted network traffic features where appropriate.
- Store timestamps consistently.
- Maintain data integrity and prevent duplicate records where necessary.
- Implement pagination for large network traffic records.
- Use database transactions for critical operations.
- Apply appropriate database security and access controls.
- Optimize database queries for large-scale network traffic analysis.

### 6. Data Storage Considerations

CIC-IDS2017 contains a large volume of network traffic records and numerous features.

Therefore:

- Preserve the original dataset files in CSV or Parquet format.
- Do not unnecessarily duplicate the entire dataset in PostgreSQL.
- Store processed records and relevant detection results in the database.
- Keep trained ML model files separately from the database.
- Store model file paths and version information in `model_versions`.
- Consider batch insertion and bulk processing for large datasets.
- Use database partitioning if traffic records grow significantly.

### 7. Future Scalability

The database architecture should allow additional functionality in future versions, including:

- User authentication and role management.
- Multiple security analysts and administrators.
- Advanced threat intelligence.
- Automated incident response tracking.
- Detailed model evaluation history.
- Real-time network traffic monitoring.
- Additional AI agents and specialized agent workflows.

Additional tables should only be introduced when required by the actual implementation.

### 8. Expected Outcome

The final database should provide a structured and scalable storage layer for the intrusion detection system.

It should connect the machine learning detection pipeline with the Agentic AI layer, allowing the system to store predictions, analyze suspicious activities, generate security alerts, and maintain a complete history of AI agent operations.

**Recommended Initial Database:** PostgreSQL

**Initial Core Tables:** 10

**Architecture:** Relational Database with JSONB support
